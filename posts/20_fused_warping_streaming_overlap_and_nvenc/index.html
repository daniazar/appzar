2. Priority 2: Monolithic Warping-Decoder TRT Fusion

2.1 The 5D Volumetric Warping Boundary

In the original Ditto architecture, facial deformation occurs across 3D canonical feature space: Fdeform=grid_sample(F3D,W(xs,xd))\mathbf{F}_{\text{deform}} = \text{grid\_sample}(\mathbf{F}_{3D}, \mathcal{W}(\mathbf{x}_s, \mathbf{x}_d))Fdeform​=grid_sample(F3D​,W(xs​,xd​)) where F3D∈RB×32×16×64×64\mathbf{F}_{3D} \in \mathbb{R}^{B \times 32 \times 16 \times 64 \times 64}F3D​∈RB×32×16×64×64 and the deformation field is 16×64×64×316 \times 64 \times 64 \times 316×64×64×3.

Standard ONNX export formats (opset_version=16 through opset_version=18) explicitly reject 5D volumetric grid_sample operators in torch.onnx.symbolic_opset16.py, raising:

text
RuntimeError: ONNX grid_sample symbolic operator does not support 5D input tensor shapes.

Attempting to compile a custom TensorRT plugin or decompose the 3D grid sampler into 2D slices introduces severe kernel scheduling overhead. Crucially, empirical profiling on the RTX 5090 Blackwell revealed that PyTorch's native ATen CUDA kernel (aten::grid_sampler3d) completes in just 0.72 ms0.72\text{ ms}0.72 ms!

The true inefficiency was not the grid sampler itself, but the fragmentation immediately following it:

  1. PyTorch reshapes Fdeform\mathbf{F}_{\text{deform}}Fdeform​ into (B,512,64,64)(B, 512, 64, 64)(B,512,64,64) and allocates memory.
  2. Kernel launch for warp_net.third (SameBlock2d): reads from DRAM, computes convolution, writes back (B,256,64,64)(B, 256, 64, 64)(B,256,64,64) to DRAM (16.0 MB16.0\text{ MB}16.0 MB).
  3. Kernel launch for warp_net.fourth (Conv2d): reads from DRAM, computes convolution, writes back (B,256,64,64)(B, 256, 64, 64)(B,256,64,64) to DRAM (16.0 MB16.0\text{ MB}16.0 MB).
  4. Kernel launch for elementwise occlusion multiplication: reads (B,256,64,64)(B, 256, 64, 64)(B,256,64,64) and (B,1,64,64)(B, 1, 64, 64)(B,1,64,64), performs modulation, and writes (B,256,64,64)(B, 256, 64, 64)(B,256,64,64) to DRAM (16.0 MB16.0\text{ MB}16.0 MB).
  5. Standalone TensorRT SPADEDecoder execution context: reads modulated feature from PyTorch CUDA memory.

Across a batch of B=8B=8B=8, these intermediate activations generated over 64.00 MB64.00\text{ MB}64.00 MB of redundant DRAM read/write cycles on every forward pass.

2.2 Compilation and Numerical Parity Verification

In scripts/ditto/compile_trt_fused_post_warp_decoder.py, we encapsulated this entire post-deformation graph into FusedPostWarpDecoder(nn.Module):

python
class FusedPostWarpDecoder(nn.Module):
    def __init__(self, warp_net, decoder):
        super().__init__()
        self.third = warp_net.third
        self.fourth = warp_net.fourth
        self.decoder = decoder

    def forward(self, deformed_feature: torch.Tensor, occlusion_map: torch.Tensor) -> torch.Tensor:
        # 1. Post-deformation conv blocks
        t = self.third(deformed_feature)
        f = self.fourth(t)
        # 2. Occlusion modulation
        f = f * occlusion_map
        # 3. Neural generation
        out = self.decoder(f)
        return out

We traced the network into a native FP16 ONNX graph (/app/cache/onnx/fused_post_warp_decoder_native_fp16.onnx) with dynamic batch shapes (1≤B≤81 \le B \le 81≤B≤8), and compiled two native engines using TensorRT 10.15:

  • /app/cache/engines/fused_post_warp_decoder_sm120_fp16_b8.engine (114.34 MB)
  • /app/cache/engines/fused_post_warp_decoder_sm120_fp8_b8.engine (114.13 MB)

We evaluated numerical parity on Blackwell Tensor Cores across 100 random Gaussian distributions:

  • Cosine Similarity: 1.000000\mathbf{1.000000}1.000000 (exact alignment with PyTorch FP16 reference)
  • Mean Absolute Error (MAE): 0.0004120.0004120.000412

3. Priority 5: Direct In-Process Hardware NVENC GPU Pipeline

3.1 Eliminating the Subprocess Pipe Bottleneck

Historically, video frames generated on the GPU were converted to planar YUV/NV12, copied into page-locked host memory, and pushed through a Unix pipe to an external FFmpeg process:

python
# Legacy IPC Subprocess Pipe
proc = subprocess.Popen([
    "ffmpeg", "-y", "-f", "rawvideo", "-pix_fmt", "nv12",
    "-s", "1080x1920", "-r", "25", "-i", "-",
    "-c:v", "h264_nvenc", "-preset", "p1", "-tune", "ull", output_path
], stdin=subprocess.PIPE)

proc.stdin.write(memoryview(pinned_buf))  # <-- IPC write & context switch

This model suffered from three structural flaws:

  1. IPC Context Switching: Every batch of frames triggered multiple system calls (write(), poll(), select()), causing CPU core migrations.
  2. Pipe Buffer Thrashing: The OS anonymous pipe buffer (typically 64 KB) filled almost instantaneously when delivering 1080x1920 frames (3.11 MB3.11\text{ MB}3.11 MB per frame), stalling the Python producer thread while waiting for FFmpeg's consumer thread.
  3. Double Muxing Overhead: Finalizing the video container required closing the pipe, waiting for FFmpeg's process exit, and re-muxing AAC audio tracks in a second subprocess pass.

3.2 In-Process PyAV NVENC Architecture

To resolve this, we implemented HardwareNVENCWriter in scripts/ditto/run_preprocessed_ditto.py using PyAV 18.1.0 linked against NVIDIA libavcodec hardware NVENC:

python
class HardwareNVENCWriter:
    def __init__(self, output_path: str, width: int, height: int, fps: float = 25.0, ...):
        self.container = av.open(output_path, mode="w")
        self.stream = self.container.add_stream("h264_nvenc", rate=int(fps))
        self.stream.width = width
        self.stream.height = height
        self.stream.pix_fmt = "yuv420p"
        
        # Configure Ultra-Low Latency NVENC hardware options
        self.stream.options = {
            "preset": "p1",        # Fastest single-pass NVENC profile
            "tune": "ull",         # Ultra-low latency mode
            "zerolatency": "1",    # No B-frame reordering delay
            "g": str(int(fps)),    # 1-second closed GOP
            "forced-idr": "1",
        }

6.1 Forensic Root-Cause Resolution: The Face Box Boundary Glitch

During early test iterations of chunked rendering, visual inspection identified a distinct momentary flash/glitch in the face box area appearing periodically every 16 frames (specifically frames 15, 31, 47, 63, 79, 95, 111, 127, 143, 159).

Quantitative frame-to-frame diff analysis confirmed sharp spikes at exactly these boundaries:

text
Frame 14 -> 15: diff = 13.93
Frame 30 -> 31: diff = 10.42
Frame 46 -> 47: diff = 14.35
Frame 62 -> 63: diff = 12.89

The Root Cause: Out-of-Bounds Uninitialized DRAM Memory Access

In speculative cadence mode (stride = 2), keyframes are evaluated at even indices (0,2,4,…,140, 2, 4, \dots, 140,2,4,…,14), and odd indices are infilled via SLERP. The buffer allocation used chunk_preds = torch.empty((chunk_len, 3, 512, 512)). For the final odd frame in a 16-frame chunk (k=15k = 15k=15), the indexing logic executed:

python
# Broken boundary clamp:
next_indices = [min(k + 1, chunk_len - 1) for k in idx_mid]

For k=15k = 15k=15, min⁡(15+1,15)=15\min(15 + 1, 15) = 15min(15+1,15)=15. Because index 15 had not yet been computed, chunk_preds[15] held raw uninitialized GPU DRAM bytes. The SLERP interpolation blended the valid frame 14 with uninitialized memory noise, creating a vivid digital rainbow artifact inside the face ROI box for that single frame.

The Architectural Fix

  1. Zero Memory Initialization: Replaced torch.empty with torch.zeros as defense-in-depth against uninitialized DRAM reads.
  2. Safe Boundary Clamping: Clamped boundary lookaheads to preceding valid keyframes: 
    python
    next_indices = [k + 1 if k + 1 < chunk_len else k - 1 for k in idx_mid]
  3. Pure Dense 25 FPS Standard (cadence_stride = 1): Set dense evaluation as the mandatory default for all broadcast deliverables. Because our monolithic fused TRT engine sustains 45.0 FPS45.0\text{ FPS}45.0 FPS (1.8x real-time speed) with full dense evaluation, speculative frame skipping is completely bypassed.
  4. CUDA Graph Mini-Batch Decoupling: In stream_ditto_pipeline.py, decoupled audio chunk sizes (N=4,8,16,25N = 4, 8, 16, 25N=4,8,16,25) from the static B=8B = 8B=8 CUDA Graph dimension by looping over keyframe mini-batches.
