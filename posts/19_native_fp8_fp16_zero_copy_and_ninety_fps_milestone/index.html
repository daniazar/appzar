  1. 3. Deep Dive: Eliminating 8.49 GB of Intermediate Memory Bandwidth

3.1 The Hidden Cost of Boundary Type Casting

In high-throughput deep learning pipelines, Tensor Core compute speed often outpaces GPU memory bus bandwidth.

In Part 18, our DenseMotionCore model accepted an input tensor with shape (B=8,C=110,D=16,H=64,W=64)(B=8, C=110, D=16, H=64, W=64)(B=8,C=110,D=16,H=64,W=64), consisting of 57,671,680 elements57,671,680\text{ elements}57,671,680 elements:

  • As FP16: 115.34 MB115.34\text{ MB}115.34 MB per batch.
  • As FP32: 230.68 MB230.68\text{ MB}230.68 MB per batch.

Because the legacy TensorRT engine expected DataType.FLOAT:

  1. PyTorch had to read 115.34 MB115.34\text{ MB}115.34 MB of FP16 memory.
  2. The GPU cast kernel wrote 230.68 MB230.68\text{ MB}230.68 MB of FP32 memory into _feat_buf.
  3. TensorRT read 230.68 MB230.68\text{ MB}230.68 MB from _feat_buf to feed its input layers.

This single boundary crossing consumed 576.70 MB576.70\text{ MB}576.70 MB of memory bus traffic per batch! Across 21 batches for a 6.6s broadcast clip, the memory traffic totaled over 12.1 GB12.1\text{ GB}12.1 GB.

3.2 Pure Zero-Copy Pointer Binding Implementation

By compiling with native FP16 ONNX definitions, the TensorRT execution context binds directly to PyTorch's native GPU memory pointers:

# Pure Zero-Copy Execution inside PyTorch CUDA Graph
if self.is_native_fp16 and feature.dtype == torch.float16:

        self._out_ret = torch.empty((B, 3, 512, 512), dtype=torch.float16, device=self.device)
        self.context.set_input_shape("feature", feature.shape)
        self.context.set_tensor_address("output", self._out_ret.data_ptr())

    return self._out_ret
